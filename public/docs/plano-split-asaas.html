Resumo da fricção

BYOGSubcontas
Fricção para o organizador Alta (técnica) — precisa criar conta Asaas, entender API, gerar chave. Porém: aceita CPF, sem docs, sem aprovação. Média (burocrática) — formulário simples, sem saber o que é API. Porém: exige CNPJ, selfie, aprovação 48h, renovação anual.
Fricção para o Tovia Média — criptografia de chaves, webhooks individuais, sem receita. Porém: sem risco regulatório. Média — homologação Asaas, período de avaliação, suporte ao organizador. Porém: receita recorrente, segurança melhor.
Para quem funciona melhor Organizadores técnicos, PF sem CNPJ, quem já tem conta Asaas Igrejas (CNPJ), organizadores estruturados, plano premium do Tovia
Conclusão para o público Tovia: Como pagamentos ficam apenas no plano mais caro, os organizadores desse plano tendem a ser mais estruturados (igrejas com CNPJ, associações). Isso favorece o modelo de subcontas — menos fricção técnica e mais receita para o Tovia.

SEGURANÇA Período de Avaliação Regulatória

Todo novo cliente Asaas que cria subcontas entra em período de avaliação obrigatório:

RestriçãoLimite
Subcontas de titulares diferentesMáximo 10
Cobranças por subcontaMáximo R$ 2.000
DuraçãoAté 60 dias corridos
  • Ao atingir qualquer limite, criação de novas subcontas é bloqueada automaticamente
  • Cobranças excluídas antes do pagamento recompõem o limite; estornos não
  • Splits para subcontas que atingiram limite são bloqueados
  • Assinaturas são canceladas e links de pagamento desativados ao atingir limite
  • Saldos permanecem acessíveis mesmo após bloqueio
  • Para continuar: concluir homologação regulatória junto ao Asaas (pode ser solicitada a qualquer momento)
  • Sandbox: período de avaliação habilitado por padrão, pode ser desabilitado para testes
Impacto no lançamento: Os primeiros 10 organizadores reais são o teste. Solicitar homologação o mais cedo possível para não travar a operação.

Salvar no Firestore: users/{uid}.asaasSubAccountId e users/{uid}.asaasWalletId

NOVO Onboarding da Subconta — Documentos e Aprovação

Após criar a subconta, o organizador precisa enviar documentos para aprovação (compliance do Asaas). Análise em até 48 horas.

Fluxo BaaS (recomendado):

  1. Criar subconta via POST /v3/accounts
  2. Aguardar 15 segundos (obrigatório — antes disso a API pode retornar docs incorretos)
  3. Chamar GET /v3/myAccount/documents usando API key da subconta → retorna lista de documentos pendentes com onboardingUrl
  4. Redirecionar organizador para o onboardingUrl → ele faz upload de documento + selfie (prova de vida)
  5. Prova de vida: aprovação em ~5 minutos (90% dos casos)
  6. Consultar status: GET /v3/myAccount/status

Documentos necessários:

  • PF, MEI, LTDA, Individual: Documento de identificação (RG/CPF/CNPJ) + Selfie do titular/sócio administrador
  • Associações: Documentos acima + Ata de Eleição
Se rejeitado: Novo onboardingUrl é gerado automaticamente. O organizador pode corrigir e reenviar. Salvar status no Firestore: users/{uid}.subAccountStatus = 'PENDING' | 'APPROVED' | 'REJECTED'

NOVO Encerramento de Subcontas

Para subcontas não-BaaS que nunca fizeram login e foram criadas há menos de 48h:

  • Habilitar "Validação de encerramento de subcontas pela API" em Integrações → Segurança (requer IP whitelist)
  • Encerramento é irreversível — implementar com confirmação dupla no admin
  • Condições: subconta da conta-pai, não-BaaS, sem login, criada há <48h, não encerrada

EDITAR API — Cobranças com Split

Modificar a Cloud Function createEventCharge em functions/src/index.ts

  • Antes: Descriptografa chave do organizador, chama Asaas com chave do organizador
  • Depois: Usa a chave do Tovia (conta principal), adiciona campo split na cobrança

O campo se chama splits (com "s"):

// Cobrança avulsa com split (doc oficial)
{
  customer: customerId,
  billingType: "PIX",          // ou CREDIT_CARD, BOLETO
  value: 100.00,
  description: "Ingresso — Retiro 2026",
  externalReference: `${eventoId}:${inscricaoId}`,
  splits: [
    {
      walletId: "uuid-da-wallet-organizador",
      fixedValue: 95.00             // até 2 casas decimais
      // OU percentualValue: 95.0   // até 4 casas decimais
    }
    // ⚠️ NÃO incluir sua própria wallet — o restante fica
    // automaticamente na conta emissora (Tovia)
  ]
}

// Atualizar split de cobrança existente: PUT /v3/payments/{id}
// Enviar splits: null ou [] para desativar split
// Se excluir a cobrança, o split é removido automaticamente
// Se restaurar cobrança excluída, o split NÃO volta — reconfigurar

Split em parcelamentos (3 modos):

// Modo 1: fixedValue — aplica POR PARCELA
// R$100 em 4x com split R$10/parcela = R$40 total para wallet
splits: [{ walletId: "...", fixedValue: 10.00 }]

// Modo 2: totalFixedValue — distribui o TOTAL entre parcelas
// R$300 em 3x com totalFixedValue R$100 = ~R$33,33/parcela
splits: [{ walletId: "...", totalFixedValue: 100.00 }]

// Modo 3: percentualValue — % aplicado POR PARCELA
// R$300 em 3x com 6% = R$6/parcela = R$18 total
splits: [{ walletId: "...", percentualValue: 6 }]

Split em assinaturas recorrentes:

// POST /v3/subscriptions — split funciona como TEMPLATE
// Cada cobrança gerada herda o split da assinatura
{
  customer: customerId,
  billingType: "CREDIT_CARD",
  value: 50.00,
  cycle: "MONTHLY",
  splits: [
    { walletId: "...", percentualValue: 93 }
  ]
}
// ⚠️ Atualizar split da assinatura NÃO atualiza cobranças já geradas
// Cobranças existentes precisam ser atualizadas individualmente
Regras do Split (doc oficial):
• O split é calculado sobre o netValue (valor líquido, descontadas taxas Asaas)
• fixedValue: máx. 2 casas decimais, não pode exceder netValue
• percentualValue: máx. 4 casas decimais, soma não pode exceder 100%
• totalFixedValue: distribui automaticamente entre parcelas (arredondamento na última)
• Não incluir a própria wallet no split — o restante fica automaticamente
• Sem limite de wallets por split
• Statuses: PENDING → AWAITING_CREDIT → DONE (ou CANCELLED / REFUSED / REFUNDED)
• Estorno automático: se a cobrança original for estornada, o split é revertido
• Cobranças antecipadas: split calculado sobre o valor líquido após antecipação, não o bruto
Consulta de splits: GET /v3/finance/split/statistics — retorna estatísticas. Na interface Asaas: menu "Split de pagamentos" → abas "Pagos" e "Recebidos". Filtros: nome da conta, data de recebimento, data de pagamento, identificador externo, nº da fatura, status. Exportação CSV disponível.
Proteção contra divergência: Se o valor do split exceder o netValue (ex: taxa Asaas subiu), o pagamento é bloqueado por 2 dias úteis. Webhook PAYMENT_SPLIT_DIVERGENCE_BLOCK é disparado. Se não ajustado em 2 dias, evento PAYMENT_SPLIT_DIVERGENCE_BLOCK_FINISHED cancela o split automaticamente. Implementar handler para esses webhooks.

NOVO Webhook — Divergência de Split

Adicionar handler para o evento PAYMENT_SPLIT_DIVERGENCE_BLOCK no webhook centralizado:

  • Quando o valor do split excede o netValue (ex: taxa Asaas mudou), o pagamento é bloqueado
  • O Tovia tem 2 dias úteis para ajustar o split via API

INFRA Renovação anual de dados comerciais

O Asaas exige que subcontas confirmem/atualizem dados comerciais anualmente (exigência do Banco Central).

  • Consultar: GET /v3/myAccount/commercialInfo/ → retorna commercialInfoExpiration.scheduledDate e isExpired
  • Atualizar: POST /v3/myAccount/commercialInfo/ → redefine scheduledDate para 1 ano adiante
  • Usar API key da subconta (não da conta-pai)

Webhooks de aviso:

  • ACCOUNT_STATUS_COMMERCIAL_INFO_EXPIRING_SOON — 40 dias antes do vencimento
  • ACCOUNT_STATUS_COMMERCIAL_INFO_EXPIRED — após vencimento sem confirmação
Se não renovar: Toda a API da subconta retorna HTTP 403 Forbidden. Apenas os endpoints de commercialInfo continuam acessíveis. Cobranças, splits, tudo é bloqueado. Implementar banner urgente no dashboard do organizador + email automático 40 dias antes.

Segurança

Contínuo

SEGURANÇA O que melhora

  • Eliminação de chaves de terceiros no Firestore: Não armazenamos mais chaves API de organizadores. O campo gateway.encrypted_api_key desaparece. Risco zero de vazamento de chaves de clientes.
  • Um único ponto de autenticação: Apenas a chave do Tovia é usada. Menos superfície de ataque.
  • Webhook centralizado: Uma URL, um token, uma validação. Sem tokens individuais por organizador.

SEGURANÇA O que precisa ser implementado

  • Chave API do Tovia: Mover de Firestore (config/billing) para variável de ambiente do Vercel (ASAAS_API_KEY). Nunca expor no client-side.
  • Validação de webhook: Usar header asaas-access-token com token fixo armazenado como env var (ASAAS_WEBHOOK_TOKEN)
  • Rate limiting: Manter rate limit existente no createCheckout e aplicar ao createSubAccount (3 tentativas/hora)
  • Dados bancários: Armazenados no Firestore, protegidos pela rule isOwner(userId). Nunca expostos via organizer_public.
  • Split values: Calcular no server-side (Cloud Function), nunca confiar em valores enviados pelo client
  • Validação de CPF/CNPJ: Validar no client (UX) e no server (segurança) antes de enviar ao Asaas
  • API keys de subcontas (BaaS): Gerenciáveis pela conta-pai via endpoints especiais, mas com janela de 2 horas de acesso (habilitada manualmente em Integrações → API Keys). Requer IP whitelist. Para não-BaaS, a API key só fica disponível durante o período de avaliação.
